# Methodology Architecture: Agentic Evolution of Routing-Aware Placement Objectives

**Purpose:** This note drafts the methodology architecture for CoEvoP&R. It is
written as source material for the paper's Method section, not as final
manuscript prose.

## Core Idea

CoEvoP&R treats the placement objective function as the artifact to be evolved.
An LLM agent proposes differentiable objective variants for analytical
placement. Each variant is evaluated by a cascade of EDA tools: DREAMPlace-4.0
for placement behavior, OpenTimer for fast timing feedback, and OpenROAD for
expensive but realistic routing-stage scoring. The resulting feedback is stored
in memory and compressed back into the next LLM prompt, allowing the agent to
iteratively improve the objective function using downstream routing evidence.

At a high level:

```text
Memory archive
    |
    v
Main LLM prompt
    |
    v
Candidate placement objective
    |
    v
Safety and differentiability checks
    |
    v
DREAMPlace-4.0 placement evaluation
    |
    v
OpenTimer timing estimation
    |
    v
Archive update and candidate selection
    |
    +--> elite candidates only --> OpenROAD routing evaluation
                                      |
                                      v
                               routing feedback to memory
```

The paper can present this as an agentic flow with three primary elements:
Brain, Tools, and Memory.

## 1. Brain: LLM Objective-Evolution Engine

The brain is the LLM-driven proposal module. Its role is not to directly place
cells, route nets, or optimize numerical coefficients. Its role is to synthesize
new symbolic objective functions from domain context and tool feedback.

The evolved artifact is a differentiable scalar placement objective:

```text
L_place = L_hpwl + lambda_density * L_density + L_evolved
```

where `L_evolved` is generated by the LLM from a restricted set of placement
observables, routing proxies, timing proxies, and safe mathematical operators.
Examples of allowed observables include HPWL, smooth wirelength, density
overflow, RUDY-style routing demand, pin density, macro density, fanout,
bounding-box area, net criticality, and local congestion estimates.

The objective can be expressed in two synchronized forms:

1. A human-readable mathematical expression.
2. A restricted executable implementation that can be inserted into the
   DREAMPlace-4.0 objective interface.

### Main Prompt Architecture

The main prompt should be constructed as a structured packet rather than a
free-form request. A stable prompt architecture makes the evolution loop
auditable and makes ablation studies possible.

Recommended prompt sections:

```text
[A] Role and task
You are an EDA objective-function designer. Propose a differentiable placement
objective that improves routed wirelength, congestion, and timing after routing.

[B] Objective interface
Define the exact function signature, allowed inputs, allowed operators, output
type, normalization rules, and differentiability requirements.

[C] Design and benchmark context
Summarize the benchmark family, technology assumptions, design scale, baseline
placement metrics, and known routing bottlenecks.

[D] Tool feedback
Provide compact scorecards from DREAMPlace-4.0, OpenTimer, and OpenROAD. Include
relative changes against baseline and parent variants, not raw logs.

[E] Memory context
Provide selected historical objective variants: current champion, parent
variant, diverse strong variants, and a few instructive failures.

[F] Evolution instruction
Ask for a specific operation: mutate, recombine, simplify, ablate, repair, or
explore a new routing-aware term.

[G] Output schema
Require the LLM to return a structured candidate with math, code, rationale,
expected effect, complexity estimate, and safety checklist.
```

## 2. Tools: Placement, Timing, and Routing Feedback

The tools are the environment through which objective variants receive
grounded feedback. The methodology should emphasize a cost-scaled evaluation
cascade: cheap checks are run for every candidate, while expensive routing is
reserved for high-value candidates.

### 2.1 Safety and Differentiability Checker

Before running any EDA tool, each candidate objective should pass a safety
interface:

- Uses only whitelisted features and operators.
- Produces a scalar finite loss.
- Has finite gradients with respect to placement coordinates.
- Avoids non-differentiable branches that depend on exact placement positions.
- Avoids file I/O, external processes, randomness, and hidden state.
- Satisfies shape, unit, and normalization constraints.

Failed candidates are still stored in memory, because they teach the agent what
forms are invalid.

### 2.2 DREAMPlace-4.0: Placement Behavior

DREAMPlace-4.0 is the primary placement evaluator. It tests whether the evolved
objective can be optimized inside a modern analytical placement loop.

Inputs:

- Benchmark design and placement configuration.
- Candidate objective implementation.
- Baseline objective configuration.
- Optional coefficients or normalization constants.

Outputs to memory:

- Final HPWL and relative HPWL change.
- Density overflow and legality status.
- Objective value trajectory.
- Gradient stability indicators.
- Runtime and convergence behavior.
- Optional placement snapshots or congestion proxy maps.

Use in prompt:

- Identify whether a candidate is optimizer-compatible.
- Diagnose failures such as unstable gradients, density conflict, excessive
  HPWL regression, or poor convergence.
- Select candidates that are good enough for timing and routing evaluation.

### 2.3 OpenTimer: Fast Timing Feedback

OpenTimer is used as a fast timing-feedback tool during evolution. It provides
timing estimates without requiring every candidate to pass through the full
routing flow.

Inputs:

- Placement result from DREAMPlace-4.0.
- Netlist, constraints, library, and parasitic approximation or available
  timing model.
- Candidate-specific placement features.

Outputs to memory:

- WNS and TNS deltas.
- Critical path or critical net summaries.
- Slack distribution changes.
- Overlap between objective-penalized nets and timing-critical nets.
- Timing regression flags.

Use in prompt:

- Tell the LLM whether the objective is helping or hurting critical nets.
- Encourage terms that focus routing-aware penalties on timing-sensitive nets.
- Penalize variants that improve HPWL while damaging timing.

### 2.4 OpenROAD: Routing-Stage Scoring

OpenROAD is used for final scoring of elite objective variants using realistic
routing-stage outcomes. Because full routing is expensive, OpenROAD should not
run for every candidate. It should run on archive elites, diverse promising
variants, and selected ablation variants.

Inputs:

- Legalized placement from DREAMPlace-4.0.
- Standard OpenROAD flow configuration.
- Technology and benchmark files.

Outputs to memory:

- Global routing overflow.
- Routed wirelength.
- DRC count or routing violation summary.
- Timing after routing, when available.
- Runtime and flow success/failure.
- Region-level congestion diagnostics.

Use in prompt:

- Provide the strongest downstream signal for the next generation.
- Correct proxy mistakes where HPWL or timing estimates disagree with routed
  quality.
- Create archive labels for later retrieval and analysis.

### 2.5 Cost-Scaled Evaluation Cascade

A candidate should advance through the cascade only if it passes earlier,
cheaper tests:

```text
Stage 0: static parse and objective-interface check
Stage 1: finite-value and autograd check on small synthetic placements
Stage 2: short DREAMPlace-4.0 smoke run
Stage 3: full DREAMPlace-4.0 placement run
Stage 4: OpenTimer timing estimation
Stage 5: OpenROAD routing evaluation for elites
Stage 6: cross-design validation for final candidates
```

The fitness function used for selection can combine metrics at different
levels, with the routing-stage score overriding proxy metrics when available:

```text
fitness =
  w_hpwl      * normalized_hpwl_improvement
+ w_density   * normalized_density_improvement
+ w_timing    * normalized_timing_improvement
+ w_route     * normalized_routing_improvement
- w_runtime   * normalized_runtime_cost
- w_complexity * objective_complexity_penalty
```

For candidates without OpenROAD results, the route term is estimated from
placement and timing proxies. For candidates with OpenROAD results, the real
routing term replaces the proxy estimate.

## 3. Memory: Objective Archive and Retrieval

Memory is the persistent archive of objective variants, tool results, feedback
summaries, prompts, and artifacts. It turns the loop from isolated prompt calls
into an evolutionary process.

### What Memory Stores

The archive should store both successful and failed candidates.

Suggested database entities:

```text
objective_variants
  candidate_id
  parent_ids
  generation
  mutation_type
  objective_math
  implementation_hash
  implementation_body
  complexity_score
  prompt_id
  model_id
  status
  created_at

tool_runs
  run_id
  candidate_id
  tool_name
  tool_version
  benchmark_id
  config_hash
  status
  metrics_json
  diagnostics_json
  artifact_paths

  candidate_id
  benchmark_id
  proxy_score

failure_modes

  failure_type

  repair_suggestion
```

### Selecting History for the Main Prompt

The prompt should not include the full archive. It should include a compact,
curated memory packet. Candidate selection should balance performance,
diversity, recency, and failure awareness.

Recommended retrieval policy:

1. Always include the baseline objective and the current global champion.
2. Always include the direct parent or parents of the candidate being revised.
3. Include top performers by routed score when OpenROAD results exist.
4. Include top proxy performers when routed results do not yet exist.
5. Include diverse variants from different structural families, such as
   congestion-weighted, timing-weighted, fanout-weighted, and density-aware
   terms.
6. Include one or two instructive failures that are relevant to the current
   mutation, such as gradient instability or density conflict.
7. Exclude near-duplicates unless their tool feedback differs in an informative
   way.

The memory packet can be represented as:

```yaml
memory_packet:
  baseline:
    id: HPWL_DENSITY
    summary: "Default smooth wirelength plus density objective."
    key_metrics:
      hpwl_norm: 1.000
      grt_overflow_norm: 1.000
  current_champion:
    id: C_037
    objective_summary: "Criticality-weighted local routing demand penalty."
    best_metrics:
      routed_wirelength_delta_pct: -1.5
      grt_overflow_delta_pct: -7.2
  parent:
    id: C_041
    objective_summary: "Adds clipped RUDY penalty near critical nets."
    latest_diagnosis: "Good timing, mild density conflict."
  diverse_elites:
    - id: C_018
      objective_summary: "Fanout-normalized congestion penalty."
    - id: C_026
      objective_summary: "Macro-boundary demand smoothing term."
  relevant_failures:
    - id: F_009
      failure_type: "unstable_gradient"
      lesson: "Avoid reciprocal distance terms without epsilon and clipping."
```
